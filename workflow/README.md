## execute-agent Workflow 改造实施计划

本文件用于记录针对 `execute-agent` 的「受控 Workflow 框架」改造方案，特别是围绕 **安全可控的代码开发与测试流程** 的设计与实施计划。

---

## 一、改动会影响的主要方面（系统级评估）

- **架构层：引入统一的受控 Workflow 框架**  
  - 从「当前的随调工具 / 随写代码」模式，抽象出一层统一的 **开发/测试 Workflow 引擎**。  
  - 所有涉及「写代码 + 跑测试」的行为，都必须通过这层，而不是直接散落在各个 Agent 逻辑里。  
  - 影响：整体架构分层、模块依赖关系、现有调用链（例如 `run_shell`、FS 操作等）。

- **插件层：不同工程类型的 Workflow Profile / 插件机制**  
  - 为 Vue / React / Express 等分别定义 **工程识别逻辑 + 默认命令 + 目录约定 + 常见操作模式**。  
  - 需要一个 **Workflow 注册中心 / 插件系统**，支持后续自由增加新工程类型。  
  - 影响：项目结构（新增 `workflow` 目录/模块）、类型定义、如何在运行时选择合适 workflow。

- **安全与可控性层：权限、危险等级和“两阶段提交”机制**  
  - 统一设计：危险操作分级、可写目录白名单、命令白名单、Plan→Preview→Apply 流程。  
  - 将当前「直接写/删/执行」的地方迁移到受控通道，并加入人工确认 / diff 预览接口。  
  - 影响：文件系统操作封装、命令执行封装、UI/交互层（展示 diff、确认步骤）。

- **测试与反馈层：测试执行、错误分析与修复闭环**  
  - 引入「测试-修复状态机」：限制每轮修复范围、迭代次数、失败后的策略（停止 / 求助人类）。  
  - 可能需要新增：测试输出解析工具、错误定位工具、修复历史记录机制。  
  - 影响：现有「运行测试」的逻辑、错误处理方式、日志结构。

- **配置与可发现性层：工程类型识别与自定义配置**  
  - 统一设计如何识别工程类型：文件特征、`package.json`、配置文件等。  
  - 支持通过配置文件/项目元数据覆写默认 workflow 和命令。  
  - 影响：项目初始化逻辑、配置加载模块、部分 CLI 或入口代码。

- **可观测性与调试层：日志、跟踪、回滚能力**  
  - 更结构化地记录：一次 workflow 的各个阶段、做过哪些修改、跑了哪些测试、结果如何。  
  - 与 Git / 快照 / 回收站的集成（用于回滚和定位问题）。  
  - 影响：日志系统、可能增加抽象的「变更记录」模型、与 VCS 的集成方式。

- **文档与使用模式层：用户心智模型与交互习惯**  
  - 用户会从「任意指令都可能直接改东西」→「有明确的工程类型 + 受控开发流程」心智。  
  - 需要更新：README、使用指南、权限说明、不同模式（安全 / 半自动 / 全自动）的解释。  
  - 影响：对外文档、内部开发规范、团队成员理解和使用方式。

## 二、建议的实施计划（分阶段）

### 阶段 1：架构设计与最小骨架搭建

- 明确：  
  - 通用 Workflow 状态机（阶段、输入输出、终止条件）；  
  - `Workflow` 接口/抽象（如 `detect/plan/generatePatches/runChecks/...`）；  
  - 安全策略核心概念（危险等级、Plan→Preview→Apply）。  
- 只实现一个「最小通用 workflow 骨架」，先搭框架和接口，不立刻大规模改业务逻辑。

### 阶段 2：接入一个示范工程类型（例如 React）

- 编写 **React 工程 workflow 插件**：  
  - `detect` 逻辑（如何识别 React 工程）；  
  - 默认测试/构建命令（如 `npm test`、`npm run build` 等）；  
  - 典型修改模式（改组件、hook 等）。  
- 把当前「对 React 项目的开发与测试逻辑」迁移到新 workflow 上，跑通端到端：  
  - 受控修改 + diff 预览 + 跑测试 + 失败分析 + 迭代上限。

### 阶段 3：统一安全层封装与强制接入

- 将所有文件写入/删除/命令执行封装到 **安全层 API**，禁止直接调用底层 shell/FS。  
- 实现：  
  - 危险等级判断与拦截；  
  - Plan→Preview→Apply 的真实执行逻辑（包括 diff 展示/确认接口）；  
  - 部分目录/文件的写入黑名单/白名单。  
- 在 React workflow 上充分验证后，再逐步替换其他地方的直接操作。

### 阶段 4：扩展到多工程类型与插件注册机制

- 实现 Vue / Express 等 workflow 插件，并通过统一的 `WorkflowRegistry` 管理：  
  - 注册与发现机制；  
  - 工程识别优先级和冲突处理。  
- 支持基础配置：  
  - 工程根目录配置文件覆写默认行为；  
  - 可禁用/强制指定某个 workflow。

### 阶段 5：增强测试-修复闭环与错误分析工具链

- 增加：  
  - 测试输出解析工具（结构化失败信息）；  
  - 修复历史记录与「重复无效方案」抑制机制；  
  - 针对连续失败的策略（收缩修改范围、建议人工介入）。  
- 通过一组典型任务回放，评估：  
  - 是否还存在「卡在测试环节」的现象；  
  - 是否明显减少「越改越错」的情况。

### 阶段 6：可观测性、回滚与文档完善

- 打磨：  
  - 每次 workflow 的执行日志与可视化；  
  - 与 Git 或内部快照的集成，保证每次大改可回滚。  
- 更新文档：  
  - 不同工程类型支持情况；  
  - 各种模式（安全 / 自动）的说明；  
  - 如何编写自定义 workflow 插件。
